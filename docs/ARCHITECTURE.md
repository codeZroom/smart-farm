# 아키텍처

ESP32/시뮬레이터 → `POST /api/v1/devices/readings` → Zod/크기 제한 → SHA-256 키 해시 → 서버 service_role → `ingest_reading` 트랜잭션 → 측정/통신시각/알림 저장.

브라우저 → Supabase Auth 이메일 로그인 → SSR 쿠키 세션 → 보호 레이아웃의 `getUser()` → 사용자 권한 Supabase 클라이언트 → RLS → Query 15초 polling → 그래프/통계. 장치 수집 요청에 사용자 쿠키는 사용하지 않습니다. 서비스 키는 server-only 모듈에서만 읽습니다.

## 일관성과 권한

- 수집 함수는 장치 행을 잠근 뒤 활성 상태, 미폐기 키 해시, 10초 전송 간격을 확인합니다. 측정·알림·마지막 수신을 한 트랜잭션으로 반영합니다.
- 등록 함수는 `auth.uid()`와 구역 소유권을 확인한 후 장치·기본 임계값·키 해시를 함께 생성합니다. 키 원문은 Node crypto 32바이트 난수로 생성되며 한 번 응답합니다.
- 재발급/폐기는 사용자 RLS 조회 후 서버 전용 함수에서 장치를 잠그고 기존 키 폐기와 새 키 추가를 원자 처리합니다.
- 사용자에게 장치의 통신시각·펌웨어 버전 수정이나 측정값 INSERT 권한을 부여하지 않습니다. 알림은 acknowledged_at만 수정할 수 있습니다.
- 비밀번호 로그인에는 Supabase Auth의 rate limit을 사용합니다. 수집 인증 성공 후 rate limit은 공유 DB에서 처리하므로 Vercel 인스턴스 간에도 유효합니다. 잘못된 키를 사용하는 IP별 전역 DoS 방어는 배포 시 WAF가 담당합니다.

## 알림

현재 열린 동일 유형 알림은 부분 UNIQUE 인덱스로 1개만 유지합니다. 정상 복귀 시 resolved_at을 기록합니다. 재진입은 마지막 생성으로부터 5분 쿨다운이 지나야 새 이력이 생깁니다. 쿨다운 중에도 현재 위험도는 최신 수치/임계값으로 계산합니다. 온도 이상·센서 실패·오프라인은 위험, 습도 이상은 주의입니다. 활성화되지 않은 장치는 오프라인 검사에서 제외합니다.

오프라인은 통신 이력이 없으면 생성 시각부터 임계시간을 계산합니다. 화면 상태는 마지막 통신과 현재 시각으로 판정하므로 스케줄러 없이도 갱신됩니다. 이력 생성은 `/api/cron/offline`을 외부 스케줄러가 호출해야 합니다. 알림의 ‘확인’은 상태 해결과 별개입니다. 푸시 확장 시 alerts 생성 이벤트에 outbox/queue와 별도 전송 어댑터를 붙이세요. 수집 트랜잭션 안에서 외부 푸시 API를 호출하지 않습니다.

## 조회 및 확장

1시간은 1분, 24시간은 5분, 7일/30일은 1시간 집계입니다. 최대 721행이므로 Supabase 기본 1,000행 제한으로 잘리지 않습니다. 평균은 샘플 수로 가중하며 최소/최대는 원시값 기준입니다. 대규모 데이터는 시간 파티셔닝·사전 집계·보존 기간을 추가하세요. 현재 UI는 소규모 농장 운영 기준, 최근 알림 100건입니다. 지속적인 장치 증가 시 장치 목록 cursor pagination과 알림 기간 검색을 확장해야 합니다.

## CSRF/CORS와 오프라인

사용자 변경 API는 정확한 Origin을 요구합니다. CORS 허용 헤더를 제공하지 않습니다. 장치 API는 쿠키 대신 기밀 Bearer 키를 요구하고 JSON만 허용합니다. HTTPS를 배포 전제로 합니다. SW는 오프라인 안내/앱 아이콘만 캐시하며 인증된 HTML/API/키/개인 데이터는 저장하지 않습니다. 열린 탭의 메모리 데이터는 오프라인 배너와 마지막 조회·측정 시각을 동반합니다. 새로 열면 정적 오프라인 안내로 이동합니다.

실제 제어 기능은 이 저장소에 없습니다. 추후 별도 명령 테이블, 장치 수신 인증, 명령 승인, 타임아웃/안전 정지, 결과 ACK를 설계해야 합니다.
